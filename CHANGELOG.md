## [Unreleased]

### Added

- **"A stated rationale is a claim" is now a registered OS obligation (FR-251, folding TD-382)** — a defect class with **eleven measured instances** in one project and **nine more** measured independently in a second had no entry in `core/enforcement/`, so it was undiscoverable: no `consult_when`, no registry row, nothing pointing an actor at it. Nine of the eleven were prose rather than logic, and warden had rejected four consecutive briefs purely on docstrings, comments and decision records while endorsing every implementation.
  - **The countermeasure moved from one project's `test_standards.md` into the cross-actor OS baseline** — `core/os/standards.md` gains a "Claims and Evidence" section (`tier: boot`, `scope: universal`), so it reaches an actor who has never read that project. Seven rules in two groups, split by **trigger** rather than topic: three fire whenever anyone writes a sentence about a measurement, four only inside a mutation battery. A flat list would have implied the authoring rules were testing-scoped — the error that produced every 2026-08-13 instance, **none of which were in test code**.
  - **No validator, deliberately.** "This sentence was never measured" is not statically detectable, and a grep-based gate would itself be a mechanism whose claim outran its evidence. The registry row states the mechanism at its true strength — a review-time gate on the claude harness only (TD-385), honor-system at build time — and answers two questions from the row alone: *what fails if I violate this while writing?* (nothing, until REVIEWING) and *which harnesses does the gate reach?*
  - **Rule 3 was discovered by the hunt itself.** Registering the obligation produced **ten fresh instances of it**, from the forger, from warden, from sentinel and from the orchestrator. Four review rounds each closed a true-but-overscoped claim and attached a new guarantee — "cannot fork", "no byte-grep can pair them", "cannot diverge" — every one of which was the next round's defect. The pattern was named and shipped as a rule: *a guarantee is a claim about what cannot happen, and it is never measurable when written; either ship the mechanism that would detect the failure, or state the fact and stop.*
  - **The instrument was wrong as often as the prose** — three hard-wrapped-grep miscounts, a Glob that did not resolve symlinks, and a "no subprocess" that was eight. So the shipped sweep is `perl -0777`, not `grep`, and its documentation leads with what it cannot do: it cannot tell a rule statement from a quotation of one, its `no X can` arm is word-count sensitive, and it cannot pair reworded copies. Six carriers of rule text are enumerated once, in `MAINTAINING.md`; five are swept by hand and `core/os/standards.md` propagates to none of them.

### Fixed

- **`mcpCall` sent no `Accept` header, so every remote sync drain was refused at the transport with HTTP 406 (BR-094)** — the MCP Streamable HTTP transport substring-tests the raw `Accept` header for `application/json` **and** `text/event-stream` and refuses before any dispatch, which is why the failure arrived as a transport 406 carrying a JSON-RPC envelope rather than as a tool error. `igris sync data` and `igris boot-sync` therefore failed their drain on every run — `boot-sync` reported `queue_drain.ok: false` beside `brain_pull.ok: true`, which reads as a partial outage and was fully deterministic (`igris_brain_pull` does not go through `mcpCall`). Nothing was lost, because the queue is preserved on failure — but nothing drained either, and the backlog grew monotonically: **22 entries in `moca-ai-agent`, 6 in `fifty-dev`**, and the standing "MCP unavailable, wrote to the filesystem fallback" line in that project's handoffs was this, banked to a queue that could not empty. Measured live against the remote on 2026-08-24: the same POST answers **406 without the header and 200 with it**.
  - **The header alone does not fix the drain, and shipping only that line would have looked like a fix while leaving it broken.** With `Accept` added the transport returns HTTP 200 whose body is a Server-Sent-Events frame, not JSON — `enableJsonResponse` defaults to false and the brain never sets it, so the transport path ALWAYS answers a POST with SSE. That body reached `JSON.parse`, threw, and landed in BR-080's `indeterminate` tier. Measured, drain-only against the live remote: **before, HTTP 406; header only, `returned HTTP 200 but the result could not be read`; header plus the SSE reader, the brain's own summary echoed back.** So `mcpCall` now also selects its reader from the response content type and correlates the frame on the JSON-RPC id it sent.
  - **That id has to be per-CALL, and the first cut of this fix got it wrong in a way that re-opened BR-080's loss class.** The correlation was written against a module-scope `MCP_REQUEST_ID = 1`, so it checked the call CLASS and not the call. The SDK transport demultiplexes replies by JSON-RPC id **per transport** (`_requestToStreamMapping.set(message.id, streamId)`, read back when the response is written — verified in the vendored SDK), and the brain funnels every session-less POST into ONE session (`activeSessions[activeSessions.length - 1]`). SSE is only reachable when that session list is non-empty, so **any run that observes SSE has by definition proved a co-tenant exists to collide with**. Two concurrent `igris sync data` / `boot-sync` runs would therefore enter one transport with the same id, the second mapping would overwrite the first, and each run would read the other's success envelope as its own — `dispatchEntry` counting an entry the brain never received as replayed, then `finalizeDrainSnapshot(_, true)` unlinking the only copy of it. The id is now a fresh `randomUUID()` per call, which also removes the server-side stream collision for **every** client of this brain rather than only for our reader.
  - **A frame that is not this call's answer stays a defined unknown.** The reader returns `null` rather than reading whichever frame looked most like a reply, and `null` is routed by `classifyToolCallBody` to the indeterminate tier, which never authorises deleting a queue entry (BR-080). Reading the SSE stream does not widen what counts as success.
  - **Correlating on the id ALONE was not enough to support the claims made about it.** Two comments — one in `sync-data.test.ts`, one three lines above the code in `sync/data.ts` — asserted that an SSE 200 reaches `classifyToolCallBody` as a parsed JSON-RPC envelope or as `null` and **never** as a bare non-envelope object. That was false: an id-only reader returns `{"id":<ours>,"junk":true}` verbatim. Rather than narrow the sentence, the reader now also requires `jsonrpc: "2.0"` and one of `result` / `error`, so the claim holds by construction. Those two conditions plus the id form a **conjunction**, and a single fixture violating all of them arms none of them — measured: deleting either shape check alone left such a case green because the other still refused the frame. Each condition therefore has a fixture violating exactly one, with a same-shape control that restores only the missing key. The result/error check also has **no** observable at the drain layer (`classifyToolCallBody` routes a result-less object to indeterminate anyway), so its assertion is on `mcpCall`'s `json` — the value the prose is actually about.
  - **Unbounded response buffering, newly meaningful on a streaming media type.** `timeout` on a node request is a socket IDLE timeout, so it never fires on a peer that keeps emitting — and SSE is designed to stay open, behind an nginx configured `proxy_buffering off` with `proxy_read_timeout 86400`. `mcpCall` now caps accumulation at 8 MiB and settles an oversize response as a transport failure, which is fail-safe on both callers (exit 1 on the drain; not-replayed, queue preserved, on an entry). **Recorded, not fixed:** the cap bounds MEMORY and not TIME — a slow trickle stays under both the cap and the idle timeout, and there is no wall-clock deadline on the whole response. `syncPull` and `healthCheck` remain unbounded on purpose, because a `/sync/pull` body legitimately carries brain deltas (128m on this vhost) and a cap sized for `tools/call` would refuse real pulls.
  - **A comment already recorded the defect while the suite stayed green, and that comment is now the assertion.** `sync-data.test.ts` carried a note that `mcpCall` sends no `Accept` header, used to justify an unparseable-200 fixture; the loopback could neither capture request headers nor answer with a second content type, so **no fixture in the file could see an outbound-header defect at all**. The note is replaced by an assertion on what the CLI sends, that fixture moved to a body nothing can parse (an nginx 502 page), and the SSE shapes got their own cases. **Twelve mutations, re-measured against the final tree, giving ten distinct red sets:** dropping the header and dropping **either** media token on its own all red the same single case (the header assertion); deleting the content-type branch reds **six** (the SSE-read case, both shape cases, the SSE replay case, boot-sync's new SSE arm, and the byte-cap control, which pads with SSE comment lines and so rides the same branch); deleting the id correlation reds two; reverting the per-call uuid to a module constant reds one; deleting the `jsonrpc` check reds one and deleting the `result`/`error` check reds a different one; neutralising the byte cap reds one and setting it to 1 byte reds 28 (the cap's own control among them); pointing boot-sync's SSE fixture at `application/json` reds only that new case; and feeding case 3b's unparseable body a readable success envelope reds one. This sentence has been corrected three times, and the lineage is recorded rather than smoothed, because every correction was the same defect at a smaller scale. As first written it read **"Four mutations, four distinct reds"**; that undercounted the mutations actually run. Its replacement read "six mutations, four distinct red sets", which was right for the round-1 tree. The round-2 rewrite read "eleven mutations … nine distinct red sets … the content-type branch reds five", and all three of those figures were wrong — two of them refutable from the sentence's own enumeration without running anything. The figures above are the measured ones. No per-mutation red count is quoted from any earlier version, because no earlier version stated one: a comparison against figures that were never recorded would be the same invention this entry exists to name.
  - **`remote-push.ts` omits `Accept` too and is deliberately unchanged** — it POSTs to `/sync/push`, which is a plain Express JSON route on the brain (`app.post('/sync/push', express.json(...))`), not the Streamable HTTP transport, so no `Accept` validation runs on it. Verified at the route rather than taken on trust; changing it would be a change with no measured defect behind it.
  - **What drained, and what did not.** `fifty-dev` drained all 6 entries live and exited 0; `boot-sync --project fifty-dev` reported `queue_drain.ok: true` with `drained: 1` on a seeded row where the pre-fix build reported `{ok: false, drained: 0}` and the 406. `moca-ai-agent` replayed 4 entries and then stopped at entry 4 on a **TD-395 create-collision refusal** — `BR-169` exists remotely at 3,005 bytes while the local cache file has since grown to 6,330 with a phase-0 work log, so the guard correctly refused to overwrite different content. That is a data conflict needing an operator decision, not a sync defect; the queue was preserved byte-identical. **The census over those 22 entries measured ONE predicate and is restated here as such:** each `brief_create`'s local cache file was hashed against the remote row, so what it establishes is that **21 of 22 clear the TD-395 create-collision guard and exactly 1 is blocked** — not that 21 would replay. The 9 `brief_sync` rows were excluded from the hash for the sound reason that they carry no content to collide, but that also means **nothing was measured about whether they clear the gateway's strict-input gate** — and a `/hunt`-queued `brief_sync` lacking `title` is exactly BR-080's live rejection class, pinned in `sync-data.test.ts`. Whoever drains this queue should expect the create-collision to be the first blocker, not the only one. Note also that `finalizeDrainSnapshot(snapshot, false)` restores the queue byte-identical on failure, so the 4 entries already replayed **will** be replayed again — the resolution needs an idempotent-safe approach, not just a decision about which copy of `BR-169` wins. `igris-ai`'s single queued entry failed at phase 1 on a literal `~` in its `cache_path` that the resolver did not expand, before any HTTP call was made — fixed in this same release by **BR-096**. What remains is **TD-409**'s amplifier: the batch still halts on the FIRST unreplayable entry, so a future dead entry re-stalls every drain.

- **The writer and the reader of the session handoff file never agreed on shape, so every REST handoff since 2026-08-07 parsed to an empty resume block (TD-360)** — `/rest` §3's template wrote `## Resume Point` and `## Next Session Instructions` as HEADINGS; `parseField` (`cli/src/verbs/session.ts`) matched only a single-line inline `**Label:** value`. Neither surface was wrong on its own — they simply never agreed, so `igris session gather` returned `resume_point: ""` and `next_steps: ""` for every handoff written to the template, and `/boot` §5 rendered a blank resume. **`**Mode:**` worked the whole time for the single reason that it happened to be written inline.** The same disagreement existed inside the CLI: `buildLiveFileContent` emitted `## Next Steps` as a heading while its own doc comment claimed "a stable shape for downstream parsers", so `register --seed-next-steps` carried `""` forward. The failure was invisible for two and a half weeks because **a blank resume block renders identically to a session with nothing to resume** — it surfaced only when an operator knew he had rested and refused to believe a cold-start report.
  - **The fix is ADDITIVE on both writers, not a replacement.** `core/skills/rest/SKILL.md` §3 and `buildLiveFileContent` now emit `**Resume Point:**` / `**Next Steps:**` as collapsed one-line machine labels **inside the `## Status` block, beside the prose sections that stay exactly where they were**. The value appears twice by design: collapsed for the parser, verbatim under its `##` heading for the human, where it may run to several lines. Dropping the prose would have broken human readers and the existing `## Next Steps` assertions; dropping the machine line is the defect itself.
  - **A bounded heading fallback recovers handoffs already written under the old template (D-360-b).** Without it the first `/boot` after shipping would still show a blank block — indistinguishable from the fix not landing. Inline-form-first-wins, then `^##\s+<Label>\s*$` returning the first non-empty, non-`---`, non-`##` line beneath, stopping at the next `##`, with the **FIRST** matching heading authoritative. Reverting `parseField` to inline-only reds 4 tests; removing only the inner `break` reds exactly 1; removing the outer `break` reds exactly 1 — that outer bound shipped as a comment killed by no mutation until a test was added for it.
  - **Verified end-to-end on a genuine pre-TD-360 handoff.** `igris session gather` against `session/instances/0309328d-….md` (dated 2026-08-21, written under the old template) now returns `resume_point: "**Last Active:** TD-408 (Done, shipped 1eb88c5)"` where it previously returned `""`. **Its two limits are stated rather than smoothed over:** the fallback reads a LINE and does not re-parse it, which is why the recovered value is the raw `**Last Active:**` row; and `next_steps` correctly stays `""`, because that file carries `## Next Session Instructions` and the pre-TD-360 template had neither a `**Next Steps:**` label nor a `## Next Steps` heading, so there is nothing to recover.
  - **Why a covered code path hid this: every test fed the parser the shape it wanted.** Six inline fixtures in `session-gather.test.ts` plus one in `awaken-verbs.bats`, none constructed from the template anything in production actually writes. The regression test now READS `core/skills/rest/SKILL.md`, extracts its §3 fence and substitutes per-slot sentinels, so it goes red again the next time the template drifts; four staleness arms fire with distinct messages. The false doc-comment claim was **deleted, not restated**, and replaced by a consumer census in which each of the four bold labels names a verified reader — two of whose citations were themselves refuted in review and corrected.
  - **The convention this established is written down** in `coding_guidelines.md` §13: *a file read by BOTH a parser and a human gets two surfaces — a collapsed machine line beside the prose section — and changing a shape obliges a bounded fallback for content already written under the old one, published at its measured reach.*

- **Instance liveness measured a shell that had already exited, so every instance — including the one actively running — classified as `dead` (TD-411)** — `resolveOwnerProcess` resolved an instance's owning process as `IGRIS_INSTANCE_OWNER_PID ?? process.ppid`. The override is wired nowhere, so the fallback was always taken, and on the claude harness every tool call spawns a **fresh short-lived shell** — `process.ppid` named a process that was already gone by the time any reader checked it. Measured 2026-08-21: 5 of 5 recent `igris-ai` instances stored a pid `ps` reports NOT RUNNING; `igris session gather` listed the **currently running** instance in `crashed[]` while `siblings[]` was empty, so `crashed[]` had accumulated every instance that ever ran (13 for this project). The classifier was never at fault — it behaved correctly on the pid it was given, and the pid was wrong every single time.
  - **Resolution is now tiered and ends in `null`:** `IGRIS_INSTANCE_OWNER_PID` → a harness-ancestor walk over ONE `ps -Ao pid=,ppid=,comm=` snapshot → `null`. Deleting `?? process.ppid` is the load-bearing line. A `null` owner is a **defined unknown**, not an error: no owner metadata is recorded, `classifyInstanceLiveness` returns `unknown_no_metadata`, and `buildGatherDigest` routes that to `siblings[]` — noise, never a false crash (D-411-c). Every walk failure lands there: an unmeasured harness, a bare-terminal run, `ps` unavailable, a renamed process, or a harness that is not an ancestor at all.
  - **THIS IS NOT A CROSS-HARNESS FIX AND IS NOT SHIPPED AS ONE.** `HARNESS_PROCESS_TABLE` ships **one measured entry — `claude`** — because claude is the only harness whose owning process was observed as an ancestor of a live tool shell from inside that harness (darwin 25.5.0 / arm64, 2026-08-21). The other **five degrade to `unknown_no_metadata`**: `codex` and `gemini` run as comm `node`, the igris CLI's own process name, so no unambiguous matcher exists; `opencode` and `antigravity` have distinctive comms whose ancestry over a tool shell was not observed; `cursor-agent` re-execs through a wrapper. A generic "nearest non-shell ancestor" heuristic was explicitly **rejected** rather than used to manufacture coverage (D-411-b) — a wrong pid is worse than no pid, and a heuristic makes the wrongness invisible again.
  - **The env override was measured undeliverable, not merely unwired.** Hooks are subprocesses whose environment does not reach a later tool call, `cli_targets` is descriptive-only, and no wrapper exists for 5 of 6 harnesses — leaving only the operator's shell rc, which is wrong under any nested shell and fails *silently by falling back*, reproducing the same bug undetectably. It is retained as tier 1 because it is the right escape hatch for a wrapper or CI, not because it is the mechanism (D-411-a).
  - **`liveness_status` stopped being a write-time constant, on the CLI side only.** Registration derives all three `liveness_*` columns through the same `classifyInstanceLiveness` path a reader uses, and `igris instance list` now OVERWRITES the stored stamp with the derived value instead of shipping both one key apart (D-411-d). The column is a last-observed stamp that no CLI reader trusts. The brain MCP's `handleInstanceList` still renders the stored value verbatim, and `handleInstanceState` still stores a caller-supplied one — that surviving divergence is **TD-412**, deliberately out of scope here.
  - **The two conventions this established are written down** in `coding_guidelines.md` §8: *degrade to a defined unknown, never to a wrong-but-plausible value*, and *a per-environment identity table is a MEASUREMENT, not a belief — no entry without an observation*.

The fix is four-pronged, all in `brain-mcp-server/src/`: (1) **fire-loop correctness fix** in `schedules/daemon.ts` — `next_run_at` is now anchored to a stable fire-start instant (was recomputed from a post-handler `new Date()` that drifted into the past under handler latency), the SELECT-due → claim → advance-`next_run_at` sequence runs inside a single `BEGIN IMMEDIATE` transaction (the async handler runs OUTSIDE the lock), a strengthened double-fire guard rejects a sequential re-fire within the same cron slot, and a re-entrancy flag stops a `recalculate()`-triggered tick from overlapping one already in flight; (2) **unconditional concurrency cap** in `subconscious/verifier.ts` — a process-wide FIFO semaphore (cap 2) bounds concurrent `claude -p` spawns, with the permit released on both the success and the spawn-failure paths (the cap is not gated on `config.subconscious.enabled` because that flag does not gate this spawn path); (3) **stdio teardown fix** in `index.ts` `runStdio()` — `process.stdin` `'end'`/`'close'` now trigger one idempotent shutdown shared with the SIGINT/SIGTERM handlers, so a Claude Code session that simply exits reliably tears down its server (the 14-day-old orphan in the diagnosis proved teardown never happened); (4) **per-client pidfile registry + opportunistic reaper** in the new `stdio-lifecycle.ts` — each stdio server registers a pidfile keyed by parent PID under `~/.igris/brain-mcp-server.pids/`, and on boot every server sweeps the registry, SIGTERM-ing only provably-orphaned instances (alive server whose recorded parent is dead) while leaving live-parent servers untouched — never `pkill`, never SIGKILL. (BR-067)

- **Sync queue drain fails wholesale on multi-row chunks** -- the `/sync/push` HTTP handler wrapped all SYNC_TABLES `mergeRows` calls in one global `db.transaction()`. A single bad row in any table (e.g., a `brief_files` row with `content` shaped as a serialized Buffer object that better-sqlite3 can't bind) aborted the whole transaction, the generic catch returned HTTP 500, and all rows in the chunk were reported as failed — accumulating ~5,000 rows in `sync_queue` over a 20-hour incident. Fix is multi-pronged: server-side per-table transaction isolation with sqlite_master preflight (BR-064 carry-over) and a new HTTP 207 Multi-Status response shape (`{ok, results, errors}`) for partial-failure visibility; row-level try/catch in `mergeRows` that returns a `failures` array with per-row table+key+error diagnostics; new `CHUNK_SIZE_LIMIT_DRAIN` constant (256 KB, was 5 MB) on the drain path with bisect-on-failure that isolates a single bad row in log2(N) push attempts and surfaces it with a specific `"HTTP 207 — table=X key=Y"` error message instead of generic `"HTTP 500"`. Auto-push (`pushTables`), `handleBrainPush`, and `handleSyncQueueDrain` all updated for the new response shape — failed tables stay at their old `last_push_at` horizon and rows are queued with the table-specific error, instead of advancing past the failure as before. 18 new regression tests (15 in `sync-push-isolation.test.ts` covering the server handler, 3 in `auto-push-207.test.ts` covering the auto-push partial path). Auto-push hot path keeps the 5 MB chunk cap; only the drain path is bounded. (BR-066, addresses MG-014).

## Release Philosophy

Igris AI follows semantic versioning:

- **MAJOR** version: Incompatible API changes
- **MINOR** version: Backwards-compatible functionality additions
- **PATCH** version: Backwards-compatible bug fixes

### What's Tracked

- Core system changes (Igris AI)
- Plugin changes (tracked separately in plugin repositories)
- Documentation improvements
- Bug fixes
- New features

### Release Process

1. All changes documented in this CHANGELOG
2. Version updated in `version.txt`
3. Git tag created for version
4. GitHub release created with notes
5. Community announcement
